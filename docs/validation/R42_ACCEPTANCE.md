# R4.2 向量存储验收（2026-10-15）

**结论：采用标准库 binary64 保存新库向量。万条 × 1024 维时，完整本地查询中位数从1588降到341毫秒，新建库从244降到92 MiB；全部向量数值和63组配对排名一致。仍是 O(n·d) 精确扫描，没有改变相关性策略。**

本轮起点为 `b30a666`。未调用真实模型、读取 `.env` 密钥、迁移真实记忆、运行旧 LoCoMo 或推送。新旧格式共用同一评分、作用域过滤、增量嵌入与上下文预算。

## 比较方法与门槛

先用1000条向量做解码可行性检查，再在完整测量前将以下条件写入脚本：三种规模100/1000/10000、1024维、相同条目ID和数值；全部向量与排名一致；万条载荷至多为JSON的40%、热查p50至多为一半。完整矩阵只执行一次，没有按结果改阈值或择优重跑。

- 使用 `scripts/r4_scale.py --compare-storage`，复用已有离线规模工具；确定性高维合成向量来自与R4相同的生成规则，不代表真实embedding的语义质量。
- 从同一临时事实库复制两份，分别使用schema 4 JSON和schema 5 binary64；按正常 `SemanticIndex.index/search` 路径调用。阈值固定0.01用于机械对照，不是产品阈值或质量校准。
- 每种规模每组测新连接首查一次、热查20次，按查询轮换两组执行顺序；返回4条，语义通道最多50条后做相同的词法融合。首查不是操作系统冷缓存。
- 另外将JSON库复制到临时目录，显式转换并核对全部向量、事实、来源与FTS；转换允许临时1 GiB容量以测量日志开销。**正常建库/查询仍用默认256 MiB，本轮未提高产品默认容量。**
- 环境为本机macOS arm64、Python 3.12.14。一次小样本测量只说明该数据/机器的开销，不是稳定尾延迟或真实模型总响应速度保证。

万条查询约快4.65倍，向量载荷减少约64%，新建库物理大小减少约62%。单独扫描并解码向量约1329/93毫秒，说明此前表示开销确实是主要瓶颈。原本Python精确内积仍保留，复杂度未变，不能外推为任意规模低延迟。

三种规模均满足：

- 每个向量数值、模型标识与条目ID一致；事实、来源与词法索引一致。
- 每组21次查询返回相同的有序ID，共63组配对；索引始终为完整hybrid。
- 正文各嵌入一次，每批至多16条；21个查询各使用一个本地替身向量，没有重嵌入旧正文。
- 显式转换保留向量与事实；重复转换的改写条数为0。

数值采用固定小端64位浮点编码，保留原Python float精度，不重新归一化。未选择float32，避免为本轮空间优化再引入量化误差和阈值/同分排序变化。

## 已有数据库的处理

新空库使用schema 5，直接保存BLOB。现有schema 4保持JSON读写，打开数据库不会转换向量。schema 1–3仍沿用原有升级到schema 4的行为；缓存格式升级单独显式进行。

宿主 `MemoryStore.compact_vectors()` 在同一事务内本地转换向量并升级版本，不调用embedding、不改变事实、来源或向量模型标识。损坏数据或容量检查失败会回滚到完整旧格式。此接口不是模型工具；真实库需先授权、关闭其他使用者并备份。schema 5不能被旧版程序直接打开，回退使用转换前备份。

**转换不会让既有数据库文件自动变小。** 万条转换耗时约2.52秒，观测数据库和事务日志峰值478.54 MiB；转换后文件仍243.62 MiB，有30,002个空闲页面可复用。接近默认256 MiB容量的旧库会因日志空间不足而回滚；需要另行审查维护空间与限额，不能按新建库92 MiB估计转换峰值。没有自动VACUUM、删除原始事实、清空缓存后重新付费嵌入或暗中提高上限。
